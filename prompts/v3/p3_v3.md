# P3 V3 — Production Semantic Review Prompt

> [!NOTE]
> **V3 — production/chained workflow.**
> This prompt is the third step of the automated pipeline (`backend/pipeline.py`).
> It receives the validated outputs of P1 and P2 automatically.
> Its output is validated by Pydantic (`P3Review` schema) before being passed to P4.

---

## System Prompt

```
Independently compare the source, analysis and target program.
Look for changed behaviour, missing branches/functions, type conversions, integer division,
overflow, null handling, collection/indexing differences, exception behaviour, ordering
assumptions, I/O mismatches and boundary errors.
Do not assume correctness.
Do not invent defects; explain evidence.
Distinguish definite defects, risks and questions.
Return ONLY valid JSON. Do not claim tests ran without test evidence.
```

---

## User Prompt

```
Perform an independent semantic review of the following translation from {{source_language}} to {{target_language}}.

Source Language: {{source_language}}
Target Language: {{target_language}}

Original Source Code:
<<<SOURCE_CODE_START>>>
{{source_code}}
<<<SOURCE_CODE_END>>>

P1 Static Analysis:
<<<ANALYSIS_START>>>
{{analysis_json}}
<<<ANALYSIS_END>>>

P2 Translated Code:
<<<TRANSLATION_START>>>
{{translated_code}}
<<<TRANSLATION_END>>>

Return ONLY valid JSON with these exact fields:
{
  "overall_assessment": "<PASS | PASS_WITH_RISKS | FAIL>",
  "findings": [
    {
      "severity": "<definite_defect | risk | question>",
      "location": "<function name, line reference, or construct>",
      "explanation": "<what the problem is and what evidence supports this finding>",
      "correction": "<suggested correction or action to resolve this finding>"
    }
  ],
  "summary": "<one paragraph overall assessment of the translation quality and key risks>"
}
```

---

## V3 Improvements Over V2

- **Automated inputs:** `analysis_json` is the validated P1 output; `translated_code` is extracted from the validated P2 output — both provided by `pipeline.py`
- **Pydantic enforcement:** Output validated against `P3Review` schema (including `Finding` sub-schema)
- **Independent framing:** System prompt says "Independently compare" to reduce anchoring
- **Evidence requirement:** "Do not invent defects; explain evidence" — findings without evidence are invalid
- **Low temperature:** Consistent with other steps for reproducibility

## Severity Definitions

| Severity | Meaning | Action Required |
|---|---|---|
| `definite_defect` | A behaviour difference that can be demonstrated from code inspection | Must be fixed before using translation |
| `risk` | A potential issue that may or may not manifest depending on inputs or runtime | Requires human review; include targeted test |
| `question` | An ambiguity where the reviewer cannot determine correctness without more information | Human must clarify before trusting translation |

## Review Categories (from system prompt)

The model is explicitly directed to check:
1. Changed behaviour (different output for same input)
2. Missing branches or functions
3. Type conversions (implicit narrowing, widening)
4. Integer division differences
5. Overflow (Python int is unbounded; Java int is 32-bit)
6. Null handling (None vs null vs nullptr)
7. Collection / indexing differences
8. Exception behaviour and types
9. Ordering assumptions
10. I/O mismatches
11. Boundary errors

## Schema Reference

See `backend/schemas.py` → `class P3Review(BaseModel)`, `class Finding(BaseModel)`.
